# Game-day report: API kill and graceful restart on Compose

- Date: 2026-09-27 (times below are UTC)
- Environment: local Docker Compose (`docker compose -p hg10`), Product commit `a5a9053`
- Scope: local only; no Live Demo, Azure, Kubernetes, or Terraform involvement
- Outcome: rooms survive both an API kill and a graceful restart because Redis runs in
  its own container. Web-policy clients rejoin the running match in about 1 s after a
  graceful restart and about 10 s after a kill. This drill found no bug in the API's
  handling of the fault. It did turn up an unrelated Compose tracing bug, described below.

## Setup

- Stack: `docker compose -p hg10 up -d` (Web, API, Redis, OpenTelemetry Collector, Tempo).
  Redis runs with `--save '' --appendonly no`; the API has no Compose restart policy.
- Load: `node tests/load/harness.mjs --step-seconds 60 --runtime-summary-file <file>` with
  `docker compose -p hg10 logs -f --no-log-prefix api` appending to that file. At the
  fault the harness was in `ramp-5-rooms`. 41 rooms were in Redis (including idle rooms
  left over from earlier runs) and 20 sockets were open.
- Probe: an ad hoc two-player client (easy, 4 seats) that follows the Web reconnect
  policy in `apps/web/src/multiplayer/socket-protocol.ts`. After a 1012 close it retries
  after 0–1 s of jitter; after any other close it backs off exponentially, capped at 5 s.
  It readies, starts, and continues matches. It does not ring. It logs close codes,
  reconnects, the revision and reveal sequence on reconnect, and reveal gaps above 2.5 s.
- No-fault reference, the same harness command on the same stack: all six steps pass,
  0/1909 client errors, server tick p95 109–143 ms.

## Drill A: `kill` (SIGKILL, no close frames)

### Commands

```sh
docker compose -p hg10 kill api
# 5 s later
docker compose -p hg10 start api
```

### Timeline

| Time | Event |
|---|---|
| 03:32:34 | Harness and probe start |
| 03:34:38 | Probe match 2 starts |
| 03:34:53 | Last summary before the fault: 41 rooms, 20 sockets, tick p95 126 ms, 86 samples |
| 03:35:04.9 | `kill api`: every socket closes with 1006 |
| 03:35:04–10 | Probe reconnect attempts fail with 1006 after backoff delays of 0.2, 0.6, 0.9, 3.0, and 4.6 s |
| 03:35:10 | Harness aborts (see below). `start api` issued |
| 03:35:11.5 | Uvicorn running (1.5 s after `start`) |
| 03:35:14.3 / 14.7 | Both probe players authenticate: phase `playing`, same match, revision 108 (106 before the kill) |
| 03:35:26 | First summary after the restart: tick p95 **6084 ms**, 88 samples |
| 03:35:41 | Tick p95 back to 113 ms |
| 03:36:18 | Probe match 2 ends normally. Match 3 starts at 03:36:48 |

### Observed behavior

- Harness: aborted with `client error rate exceeded 2%`, 2.15% (5/233), reason
  `unexpected socket close 1006` (5). The steps before the fault were within budget
  (server tick p95 117 / 110 / 126 ms). The harness counts every unexpected close as an
  error and does not reconnect, so it cannot measure recovery (see follow-ups).
- Rooms survived. The probe rejoined the same match at revision 108, two revisions after
  what it last saw, and the match ran to completion.
- The due loop resumed where it stopped and did not replay the downtime. The reveal
  sequence went from 24 to 26 across an 11.1 s gap without reveals. At the easy pace,
  replaying the whole gap would have skipped about 12 reveals.
- The 6084 ms tick-lateness p95 in the first summary after restart is expected. Every
  live room's overdue deadline is processed once on startup, and the lateness is
  measured from the original deadline. This one sample makes the same abort condition
  fire in any run that spans an API restart.
- API log: clean startup with no tracebacks.
- Harness rooms whose clients had gone kept playing to the end of their current match
  with no sockets. Tick samples in the next summaries fell from 73 to 43, 35, 22, and 11.
- About 1.5 s of the 10 s interruption was API startup. About 3 s came after the API was
  already back, because the probe was waiting on its 4.6 s backoff.

### What a player would experience

The table freezes for about 10 s and the room shows "Connecting to room…". The player
then returns to the same match with scores intact. Reveals continue from where the
authority stopped, not from wall-clock time. Nothing tells the player why the table
stopped.

## Drill B: `restart` (SIGTERM, graceful 1012)

### Commands

```sh
docker compose -p hg10 restart api
```

### Timeline

| Time | Event |
|---|---|
| 03:38:03 | Harness and probe start |
| 03:40:06 | Probe match 2 starts |
| 03:40:33 | `restart api` issued |
| 03:40:34.019 | Uvicorn `Shutting down`. Sockets close with **1012** at 03:40:34.069 |
| 03:40:34.129 | Application shutdown complete |
| 03:40:34.151–.367 | Probe seat 1 retried after 68 ms of jitter, before the API was listening, and got two 1006 failures (backoff 210 ms, then 716 ms) |
| 03:40:34.956 | New API process running |
| 03:40:35.07 / .09 | Both probe players authenticate: same match, revision 103 (unchanged), same reveal sequence 21 |
| 03:41:37 | Probe match 2 ends normally |

### Observed behavior

- Harness: aborted with 2.50% (5/200), reason `unexpected socket close 1012` (5). The
  harness treats a planned 1012 the same as a crash.
- The interruption lasted about 1 s end to end. No revision was missed, and no reveal gap
  above 2.5 s appeared. The container restarts in under 1 s because the `uv` environment
  is already on a named volume.
- The 0–500 ms Web jitter is shorter than the API's restart time on Compose. Clients that
  draw a short jitter hit a closed port first and fall back to the normal backoff. They
  still recover within about 1 s.
- API log: orderly `Shutting down` → `Application shutdown complete` → startup, with no
  tracebacks.

### What a player would experience

A blink of "Connecting to room…" for about 1 s, then the same table and turn. No score
change, no lost reveal.

## Incidental finding: local traces are never exported

This affected every drill. The API logged 918 × `Failed to export span batch due to
timeout, max retries or shutdown.` over the session. The Compose OpenTelemetry Collector
logs `Starting HTTP server ... "endpoint": "127.0.0.1:4318"`, and Tempo logs
`Starting HTTP server component=tempo endpoint=127.0.0.1:4318`. Both OTLP receivers bind
to loopback inside their own containers. Their configs in `compose.yaml` set
`protocols: http:` with no `endpoint`, and recent releases default that to localhost.
From the API container, a POST to `http://otel-collector:4318/v1/traces` returns
`Connection refused`. As a result, the local Compose trace pipeline described in
`DEVOPS.md` delivers nothing to Tempo. This is a Compose configuration bug. The likely fix
is `endpoint: 0.0.0.0:4318` on both receivers, but that was not applied or verified here.

## Follow-ups

1. Harness: add a drill mode that reconnects the way the Web client does and reports
   time-to-recover instead of aborting on the first unexpected close. With a small
   operation count, 5 closes already exceed the 2% abort threshold.
2. Harness or authority: the first summary after an API restart reports a multi-second
   tick p95 that comes only from catch-up. Either mark catch-up samples separately or
   document that a restart trips the 250 ms abort by design.
3. Decide whether a Bell Window that expires while no API process is running should be
   penalized. In the code (`_advance_room_if_due` in `authority.py`), catch-up resolves a
   Bell Window that was still open when the API died as missed, which charges the missed
   penalty. Players had no chance to ring during that window. The probe did not ring or
   record `lastEvent`, so this drill did not observe the penalty directly.
4. Fix the Compose OTLP receiver endpoints (incidental finding above).
5. Compose only: `api` has no `restart:` policy, so a crash stays down until someone runs
   `start`. The deployment targets restart the container themselves.

## Follow-up disposition (2026-09-28)

These later statuses preserve the drill results above as observations from 2026-09-27.

1. **Partly resolved.** The load harness reconnects after planned `1012` closes and records
   recovery time, as used by the [K3s rollback drill](https://github.com/optiplex331/Halligalli-infrastructure/blob/main/targets/k3s/evidence/rollback-drill-2026-09-27.md).
   A SIGKILL close (`1006`) still counts as a client error, so this is not a general
   crash-recovery drill mode. See `tests/load/README.md` and `tests/load/harness.mjs`.
2. **Documented; metric semantics are unchanged.** Tick lateness still includes the
   original deadline during catch-up, and the load abort threshold still applies. The
   6084 ms sample and its effect are recorded above; no catch-up exclusion was added.
3. **Resolved as current behavior.** Catch-up charges at most one open Bell Window as
   missed and starts the next deadline from the current time. This is documented as
   intended behavior in the [Container Apps SLO](https://github.com/optiplex331/Halligalli-infrastructure/blob/main/docs/operations/container-apps-slo.md);
   the report does not claim a separate outage-time integration test.
4. **Resolved in `v0.10.1`.** `compose.yaml` now sets both Compose OTLP receivers to
   listen on `0.0.0.0:4318`.
5. **Unchanged local behavior.** `compose.yaml` has no API restart policy and is scoped
   to daily development; target restart behavior remains owned by the deployment
   platforms. This remains a local development convenience question, not a target
   deployment gap.
